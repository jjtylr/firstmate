# The lane claim

The dispatch, written on the blackboard **before** it happens. Read this at step 4 of the cycle,
when you are about to spawn a worker, and at step 7, when the row you write releases the claim.

Between "the orchestrator decided to dispatch #100" and "a branch for #100 exists on the remote"
there used to be a window in which the dispatch existed in one context window and nowhere else.
Everything that has to see in-flight work — a second lane, a concurrent scoring pass, a restarted
orchestrator, the next cycle's pick — was blind inside it. The claim closes the window by putting
the fact where the other actors already look.

## The block

Posted as a comment on the ticket, under the AI-generated disclaimer, with the marker on a line of
its own. `validate-claim.sh` owns the marker string and refuses everything below; it runs before the
comment is posted, never after.

```
> *This was generated by AI during the drain loop.*

<!-- lane-claim v1 -->
TICKET: #<N>
BRANCH: agent/<SLUG>-<N>
LOCKS: <the resolved Locks: snapshot, or ->
DISPATCHED-ON: <YYYY-MM-DD>
PARKED: <why>              ← added on park; the claim stays open
RELEASED: <why>            ← added by hand to release a parked claim; absent otherwise
```

`TICKET` and `BRANCH` name the dispatch, and `PARKED` and `RELEASED` are annotations a later reader
adds. Two fields carry the dispatch's weight, and each is required:

- `LOCKS`, the resolved `Locks:` snapshot the collision check cleared. `-` is the written form of
  "the ticket declares none", the same convention the ledger row uses. A *missing* line is refused
  rather than read as `-`: a claim with no snapshot cleared no check, and nothing downstream can
  tell which of the two a blank line meant.
- `DISPATCHED-ON`, the ISO dispatch date. The release check dates the claim from it, so a row an
  earlier run left cannot release a fresh claim.

`validate-claim.sh` refuses a claim missing `TICKET` or `BRANCH` too. A claim written before
ADR 0007 also carries a surface line; that field was dropped, not forbidden, so a claim still in
flight when the change landed validates unchanged.

## What the snapshot asserts

**The declaration as the collision check cleared it, at that moment.** Step 2 resolves `Locks:`
from the body and every agent brief; step 3 clears it against the global locks; step 4 writes what
was cleared. Nothing re-reads the issue afterwards.

**So a post-dispatch amendment never reaches back.** A `Locks:` line changed by a brief posted
after the claim describes the *next* dispatch of that ticket, not the one in flight. Rewriting the
claim to match would retroactively change what a check already cleared, and the check would then be
a claim about declarations nobody ever measured. The scorer skips claimed tickets for the same
reason: that seam is the one place a concurrent stage could move a declaration under a decision
already made.

## Park — the ticket waits, and so does the run

When a PR falls to the PM, through an update conflict, a pin refused twice, a `concerns` verdict or
a `fail` verdict ([MERGE-PIPELINE.md](./MERGE-PIPELINE.md)), the lane it occupied is waiting on a
person, and a person is not a lane. So the claim is annotated `PARKED: <why>`.

**A park is not a release.** `claim-status.sh` answers `CLAIM-PARKED`, its own verdict word, so no
reader decides parkedness by matching the prose after the dash. Three readers act on that word.
`pick.sh` keeps skipping the ticket. `check-capacity.sh` stops counting its lane as occupied, so the
slot returns to the count. `check-holds.sh` then holds every candidate for as long as the park
stands, so above 1 lane nothing takes that slot until the PM clears it; at 1 lane that check does
not run and the next candidate takes the slot ([SCHEDULER.md](./SCHEDULER.md)). `RELEASED` beats
`PARKED` if both are written; the PM's word ends a claim whatever else is on it.

A parked claim is a findings line every cycle until the PM resolves it: only the repetition says it
is stale rather than in flight. It is the **one** claim shape that waits for a person. A dead
worker's claim does not. Step 1 releases that one inside the cycle that finds it.

## Release

`claim-status.sh <N>` is the reader, and it is the only home for the rule. Two paths release a
claim, and neither of them is a label:

1. **The ticket's ledger row** — any of the six outcomes, because a written row means the dispatch
   is over however it ended. This is the ordinary path and it needs no PM action: step 7
   writes the row, and the next pick reads the claim as released. The row must be dated on or after
   the claim's `DISPATCHED-ON`, so a row left by an earlier run of a re-readied ticket cannot
   release the claim posted after it.
2. **By hand** — a `RELEASED: <why>` line annotated onto the claim comment. This is the PM's path
   for the one claim no row is coming for: a parked PR they have finished with. A parked PR gets no
   ledger row while it is parked — the row is the release, and the dispatch is not over.

**A dead worker's claim is released by its row, like every other.** Step 1 reports
`REAP-HELD-DEAD`, and the cycle then clears the lane itself, in this order
([SKILL.md](./SKILL.md) step 1). The ticket loses `ready-for-agent` and gains `needs-info`, *then*
the cycle writes its `died` row, then the `claimed` mirror comes down. The order is the whole safety
argument. A release on its own would put the ticket back in the pick and invite a silent
re-dispatch over whatever the dead run left behind. A released claim on a ticket that no longer
carries `ready-for-agent` cannot, because the label that would qualify it for the pick is already
gone. The worktree and the branch stand. They are the only record the run happened, and salvage or
discard is still the PM's.

This is what a claim released by hand used to be for, and the reason it stopped being enough is
measured. Headless there is no PM inside the run to write the annotation, so the claim stood, the
collision check kept holding candidates against it, and one worker's death ended the run. Measured
on run #211: two iterations, nothing dispatched, nothing merged (#213).

An unreadable claim — a failed comment listing, a block with no readable date — is **held**, never
released. An unread claim is never a free one, the same reading `check-lock.sh` gets from an unread
lock.

## The `claimed` label

A mirror, for human eyes, so the tracker shows what is in flight without anyone opening the issue.
Added when the claim posts, removed when the claim is released, on both release paths.

**No script decision reads it** ([LABELS.md](../setup-engineering-skills/LABELS.md)), and where the
label and the claim disagree the claim wins. That is deliberate rather than lax: a label is one API
call away from being wrong, and a mirror that gated dispatch would be a second, weaker copy of the
record it mirrors. So a label that fails to land is a cosmetic defect, and a label removed by hand
changes nothing about which tickets the pick returns.

## Against the stage contract

- **§ 3, machine-readable, versioned, validated before posting.** The `lane-claim` marker, on a line
  of its own, with `validate-claim.sh` as its machine-owned home and the script that refuses a block
  missing it. Consumers — `pick.sh`, `claim-status.sh` — select on the same own-line definition, so
  anything the validator accepts is a comment they find, and a marker quoted in prose is not one.
- **§ 4, findings lines.** A held ticket gets one `PICK-CLAIMED` line per cycle, for as long as it
  is held. A claim nobody releases starves its ticket, and only the repetition says so.
- **§ 5, workers hold no state.** The claim is the reason a restarted orchestrator loses only the
  in-flight dispatch: what it knew is on the ticket, not in its window.
